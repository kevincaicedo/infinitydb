One engine for the cache, the ledger, the queue, the document, and the vector.

InfinityDB is an extensible key/value engine kernel — Redis-compatible on the wire, durable like a system of record, designed to grow JSON documents, Kafka-class queues, and vector search from one primitive: a per-core, append-only log. Built in the open, milestone by milestone, behind hard evidence gates.

01 / The wedge

Keep redis-cli. Keep every SDK.
Adopt progressively.

Redis compatibility is the wedge, not the ceiling. You replace systems one namespace at a time — never one migration at a time.

STEP 1 · TODAY

Point your client at it

RESP2/RESP3 on port 6379, with per-command compatibility declared in a generated, byte-diff-verified matrix — never a breadth claim. Day one, nothing about your stack changes.

STEP 2 · TODAY

Turn on durability

Durability is a property of the namespace, not the server. One command turns a cache namespace into an fsync-gated system of record — classes and loss windows documented precisely.

STEP 3 · ROADMAP

Retire adjacent systems

Model entities as JSON documents (M3), query them without a planner (M4.5), move queues onto topics (M7), add vector search (M8) — same client libraries, same node, same operational surface.

02 / The primitive

Everything is a projection of the log.

APPEND

Every durable fact is an append to a per-core, append-only log — before it is anything else.

PROJECT

The hash index, checkpoints, tiered storage: derived projections — rebuildable from the log by replay.

CONSUME

Topics and consumer groups read the same log forward. The queue isn’t bolted on — it’s the spine, exposed.

SHIP

Replication ships the log to a follower. CDC hands it to a subscriber. Point-in-time recovery replays it.

ONE PRIMITIVE

A cache is just the log with durability off. One mechanism to make correct — not five.

03 / The shape

One core, one shard, one owner.

Every key, partition, and log segment is owned by exactly one core. Each shard cell is a complete miniature database. No locks on the hot path — cells talk only through a batched, lock-free fabric.

Batch every boundary

Syscalls, fabric hops, fsyncs, and cache misses are paid per batch, never per operation. One submission per reactor iteration, by construction — and the batching metrics are CI-gated tripwires, not dashboards.

Commands that suspend

Every command is a resumable state machine: disk reads, cross-shard hops, and fsync-gated acks suspend without blocking the core. The fast path never suspends — and pays nothing for the capability.

Deterministic by design

Time, randomness, and I/O are injected. The whole node runs deterministically in simulation — every failure is a replayable seed, FoundationDB-style. Simulated disks tear writes and lie about fsync; oracles check every ack survived.

04 / Workloads

Five systems. One operational surface.

Each workload is a projection of the same kernel — and each arrives on the train with its milestone named. Two ship today; the rest are design, not claims.

01

In-memory cache SHIPPING

RESP2/3, the string/key/expiry command families, all 8 eviction policies, pub/sub. Memory-only namespaces never touch the log. Collections (hashes, lists, sets, zsets) arrive at M5.

TARGETS REDIS · VALKEY · DRAGONFLY WORKLOADS
02

Durable key-value SHIPPING

Per-namespace fsync classes, fuzzy fork-free checkpoints, parallel recovery. Acks gated on the durability watermark. Larger-than-RAM tiered storage arrives at M4.

TARGETS DYNAMODB-CLASS KV (SINGLE REGION)
03

JSON documents M3 · NEXT

RedisJSON-compatible JSON.* with JSONPath over a compact binary document tree. Mutated by path, durable by delta. Typed secondary indexes and a planner-free PartiQL subset follow at M4.5.

TARGETS DOCUMENT-STORE WORKLOADS
04

Streams & queues M7

Kafka-model topics and consumer groups on the log spine, full Redis Streams API, plus DLQs, delays, redelivery, idempotent producers.

TARGETS KAFKA-CORE · RABBITMQ-CORE
05

Vector search M8

Per-core HNSW with quantization and SIMD distance kernels. Vectors are ordinary durable records — replicated and tiered like everything else.

TARGETS DEDICATED VECTOR DBS
+1

In-database compute M10

Sandboxed WASM reducers execute inside the process, on the core that owns the data — zero network, zero serialization, transactional. Plus embedded and shared-memory modes.

NONE OF THOSE SYSTEMS OFFER THIS

A kernel, not a monolith

Documents, streams, vectors, and compute are engines attached to versioned seams — feature-gated crates, not special cases. A cache-only build compiles none of the rest: smaller binary, smaller attack surface, nothing cold in the icache. You compose what you run.

Move code to data

The same seams first-party engines use are the programmability surface: WASM reducers (M10), an embedded Rust crate and shm IPC for co-located services — and a stabilized native extension SDK after 1.0.

05 / Status

Where it actually is.

InfinityDB is in development, built milestone by milestone behind hard STOP gates — a milestone that fails its gate halts feature work. M0 (architecture proof), M1 (cache core), and M2 (durability) are complete; M2.5 is hardening the durable core into the first public tag, v0.2.0-alpha.1.

Why there are no benchmark numbers on this page: the project’s evidence policy forbids publishing a number before a validated, replicated artifact exists — and comparative numbers additionally require the competitor in the same run on the same box. Every public number lives in the claim ledger with its artifact, or it does not exist. When the ledger allows one, it appears here — not before.
