01 · ONE ENGINE, FIVE WORKLOADS

Stop running five databases.

A kernel, not a monolith: a small core — runtime, fabric, log, store — with versioned seams. Every engine below is an extension of the kernel, arriving on the train with its milestone named. Build cache-only, or build everything.

/01

Cache SHIPPING

TARGETS REDIS · VALKEY · DRAGONFLY

RESP2/3, the string/key/expiry command families, all eight eviction policies, pub/sub. Memory-only namespaces never touch the log. Per-command compat is declared in a generated, byte-diff-verified matrix.

/02

Durable KV SHIPPING

TARGETS DYNAMODB-CLASS STORES

Per-namespace durability — always, everysec, memory — group-commit fsync, fuzzy fork-free checkpoints, parallel recovery. Larger-than-RAM tiering is in dev now (M4).

/03

Documents M3 · BUILT · TAGS v0.4.0-α

REDISJSON-COMPATIBLE NOSQL

JSON as a first-class value: JSON.* + JSONPath over a compact binary tree, mutated by path, durable by default. Byte-diff-verified against RedisJSON; ships with the first public tag. Typed secondary indexes and a planner-free PartiQL subset follow at M4.5.

/04

Streams & Queues M7

TARGETS KAFKA-CORE · RABBITMQ-CORE

Topics and consumer groups built directly on the write-ahead log. Full Redis Streams API, dead-letter queues, delays, idempotent producers.

/05

Vectors M8

THE AI-ERA LAYER — IN 1.0

Per-shard HNSW + SQ8 quantization, SIMD distance kernels. Vectors are ordinary durable records — replicated, tiered, checkpointed.

/plus

In-database compute M10

NOBODY ELSE SHIPS THIS NATIVELY

WASM reducers run inside the database, on the core that owns the data. Zero network. Zero serialization. Sandboxed, fuel-metered, transactional.

02 · THE SHARD CELL

One core. One shard. One owner.

Each core runs a complete miniature database — reactor, parser, executor, keyspace slice, log writer, allocator. No other thread ever touches its data.

→Every command is a resumable state machine — the fast path completes synchronously and never pays for the capability.
→Batch every boundary: syscalls, fsyncs, fabric hops, and cache misses are paid per batch, never per op — and the batching metrics are CI-gated tripwires, not dashboards.
→Expiry, eviction, checkpoints, and compaction run under deficit-weighted budgets — tail latency is protected by construction.
→Deterministic by design: the whole node replays under simulation from a seed — every failure is reproducible.

03 · THE FABRIC

Shared-nothing, without the sharp edges.

Cells communicate only through a full mesh of lock-free SPSC ring pairs — batched, poll-integrated, credit-controlled. Cross-slot operations that fail on Redis Cluster just work here; they pay a fabric hop instead of returning CROSSSLOT.

05 · ONE SESSION

Five workloads. One connection.

A cache write, an fsync-gated durable write, a JSON document mutation, a query, a stream read — on one node, over the Redis protocol you already speak. What ships is live; what’s coming is labeled with its milestone.

Durability is a property of the namespace, not the server. The loss window is a config knob.
