Deployment

How to run an InfinityDB node beyond a quick trial: Docker with the io_uring seccomp profile, a systemd unit, what the data directory contains, which ports exist, every server flag, and the upgrade rules for the on-disk format. It is an early alpha — read the operations page for what the node does after a crash and the alpha boundary list before trusting it with anything.

Alpha exposure warning: there is no AUTH, no ACL, and no TLS until M7. Bind InfinityDB to localhost or a trusted private network only. Both paths below assume that posture.

Docker

Until the first public tag lands there are no published container images (see the quickstart’s packaging note) — build the image from the repository. The Dockerfile produces a static musl binary in a scratch-based image: no shell, no libc, minimal CVE surface.

# from the repository root, inside infinitydb/
docker build -t infinitydb:dev .

docker run --rm -p 6379:6379 \
  --security-opt seccomp=deploy/seccomp/infinitydb-seccomp.json \
  -v infinitydb-data:/data \
  infinitydb:dev --data-dir /data

The -v volume and --data-dir /data give the node durable storage; omit both to run a memory-only node (pure cache semantics, nothing survives a restart).

The seccomp profile is required

InfinityDB’s I/O plane is built on Linux io_uring, and Docker’s default seccomp profile blocks the io_uring syscalls (io_uring_setup, io_uring_enter, io_uring_register). Under the default profile the node cannot create its reactor and exits immediately with:

infinityd: cell failed: Operation not permitted (os error 1)

Three options, from most to least hardened:

  • The bundled profile (recommended): deploy/seccomp/infinitydb-seccomp.json ships in the repository. It allows io_uring while explicitly denying the high-risk container-escape syscalls (mount, pivot_root, kernel-module loading, kexec_load, bpf, ptrace, perf_event_open, keyring and clock-setting calls, and more). The file must be present on the host at the path you pass to --security-opt.
  • Strict allow-list posture: take Docker’s upstream default.json and append the three io_uring syscalls to an SCMP_ACT_ALLOW entry. Keeps the full default deny-list and adds only what InfinityDB needs.
  • seccomp=unconfined (development only): removes all seccomp filtering — local trusted machines only.
Host runs need none of this. Running infinityd directly on a host is not subject to Docker’s seccomp profile. Kubernetes and CI environments differ — some already permit io_uring, some apply the Docker default. If a containerized node exits with the error above, seccomp is the cause.

systemd

infinityd runs in the foreground, logs to stderr, and takes no signals — Type=simple is correct. A minimal hardened unit:

[Unit]
Description=InfinityDB node
After=network-online.target local-fs.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/infinityd --port 6379 --data-dir /var/lib/infinitydb
User=infinitydb
Group=infinitydb
StateDirectory=infinitydb

# Fail-stop is deliberate (see the operations page): a recovery refusal or a
# durable fsync failure is disk-integrity evidence that must reach an operator.
# Do not turn it into a silent restart loop.
Restart=no

LimitNOFILE=1048576
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/infinitydb

[Install]
WantedBy=multi-user.target

Two honesty notes worth reading before you copy that file:

  • Restart=no is a recommendation, not a limitation. InfinityDB’s deliberate exits — a recovery refusal (exit code 1), a durable fsync failure (exit code 3), a cell panic (exit code 101) — all mean the same thing: restarting will not help, and a restart loop hides the evidence. The operations page explains each exit and what to do.
  • Stopping the node is a crash, by design. There is no shutdown handshake: systemctl stop kills the process, and the next boot recovers from the log. That is exactly the crash model the durability classes are specified against — an always namespace loses nothing (every acknowledged write was fsynced before its ack), an everysec namespace can lose up to its stated one-second window, a memory namespace loses everything. If those windows surprise you, read the durability page before deploying.

The data directory

With --data-dir set, the node owns a directory tree of exactly four kinds of file — every one CRC-protected, every one swap-published atomically (write-new + fsync + rename + directory-fsync):

<data-dir>/
├─ META                     # node namespace catalog (which namespaces exist, their durability class)
├─ shard-0/                 # cell 0 — one directory per cell, recovered independently and in parallel
│  ├─ MANIFEST              # the recovery unit: checkpoint id, begin-LSN, live segment set
│  ├─ log/
│  │  ├─ seg-000000.ilog    # log segments — sealed at --segment-bytes, then immutable
│  │  └─ seg-000001.ilog
│  └─ ckpt/
│     └─ ckpt-000001.ick    # fuzzy checkpoint (a materialized log prefix)
├─ shard-1/
└─ …                       # one shard directory per --cells
  • The log is the database (law L2): segments plus the checkpoint they truncate into are the complete durable state. Back up the whole directory; a consistent snapshot of it is a valid recovery unit.
  • Segment count stays bounded in steady state: checkpoints let the MANIFEST truncate older segments (observable as log_segments_live in INFO persistence).
  • Do not edit, rename, or delete files inside the tree. Recovery treats missing or altered named state as corruption and refuses to start — deliberately (see operations).
  • Byte totals reported during load are file extents including preallocated slack — a disclosed upper bound, so du-style numbers can exceed live data.

Ports

Exactly one TCP port (default 6379). Every cell binds the same port with SO_REUSEPORT and the kernel spreads incoming connections across cells. RESP2 and RESP3 (HELLO 3) are negotiated on the same port. There are no other listeners — no cluster bus, no gossip, no metrics port: this is a single-node alpha, and observability rides INFO over the same connection.

Server flags

Flags only — no config file (a deliberate anti-goal at this stage). Verified against infinityd --help:

FlagDefaultMeaning
--port6379TCP port to listen on.
--cells4Number of shard cells (one thread and one shard-k/ directory each). Each cell recovers only its own shard, so treat the value as fixed for the life of a data directory — do not change it on an existing one.
--data-dirunsetDurable-plane root. Absent = memory-only node: the durable machinery is not just idle but absent from the hot path (measured, ledger row C15).
--ckpt-interval-bytes268435456 (256 MiB)Bytes-appended checkpoint trigger, per cell. 0 = manual only (INF.CKPT / BGSAVE).
--segment-bytes268435456 (256 MiB)Log segment prealloc/seal size.
--sync-pipeline1Durability fsyncs in flight per cell: 1 or 2, never a queue. The measured default is 1; 2 is a bounded pipeline kept as an A/B knob.
--buffers / --buf-size4096 / 4096io_uring provided-buffer pool: buffer count and per-buffer bytes.
--pin-startunsetFirst core index to pin cells to; cell i pins to pin-start + 2i (every other logical core, leaving SMT siblings free). Unset = no pinning.
--route-local-onlyoffTreat every key as local to the accepting cell — benchmark/diagnostic mode, not for real data.
--versionPrint version, git SHA, and build target, then exit.

The remaining flags in --help (the fabric-flush, execute-order, and prefetch toggles) are measured A/B levers whose defaults carry the winning arm — leave them alone unless you are reproducing an experiment.

Runtime configuration uses the Redis CONFIG surface (maxmemory, maxmemory-policy, and friends — see the compatibility matrix); per-namespace durability and eviction are set at INF.NS CREATE time (see namespaces & durability).

Upgrades & downgrades

The on-disk log uses batch frame format v2 (per-frame sequencing, ADR-0031) as of M2.5. The rules, stated plainly:

  • Reading is forever: the v0.2 line reads both frame format v1 and v2. A log written by an older alpha binary remains readable on every later alpha binary.
  • Writing is v2 only — there is no write-v1 mode. The first time a v2 binary appends to a log, that log contains v2 frames.
  • No downgrade after the first v2 write: pre-v2 binaries cannot read v2 frames, so once a v2 binary has appended, rolling back the binary means restoring the data directory from a pre-upgrade backup as well. Recovery additionally treats a v1 frame appearing after a v2 frame as a named refusal — no honest writer can produce that ordering.
  • Format changes are ADR events, not patches: each one lands with fuzzing of both formats, a crash-matrix re-run, and a fresh simulation sweep (law L9).
