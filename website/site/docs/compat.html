      Redis compatibility

      Compatibility is declared per command. A row marked full has corpus cases that CI compares with its pinned oracle (Redis 8.0.5 for the core surface, a pinned RedisJSON for the JSON commands), and a mismatch that no recorded deviation names fails the build.

      Available · alphaLaw L8
      Generated tables

      The tables on this page are rendered from docs/compat-matrix.md, which a test of the compat crate regenerates from the command registry and the corpus CI compares with its pinned oracles. They are never edited by hand, and CI fails when the committed page is stale against the matrix or the matrix against the registry and the corpus.

      Status vocabulary

      StatusMeaning
      fullEquivalent to Redis by behaviour. Recorded differences are representational only: ordering, identity payloads, opaque cursors.
      partialA documented semantic difference exists. The note says which.
      stubAccepted but inert.
      extensionAn INF.* command Redis does not have.
      internalA fabric primitive between cells, not a client surface.

      Cases counts the compared corpus executions. Evidence counts the ones that answer neither an error nor a null: a full row needs at least one, so an error-path case alone never makes a command full. A command that is absent from this table is absent from the server.

      Documented deviations

      Each entry is a justification from the diff corpus: the reply must still be well-formed RESP, but its bytes differ from Redis by design.

      HELLO

      • identity fields differ by design (L8: server/version)
      • identity fields differ; proto switch verified locally
      • NOPROTO error text verified in unit tests

      PTTL

      • same u40 clamp — the remaining TTL is measured to the bound

      INFO

      • section payloads differ (InfinityDB identity/tripwires; run_id/master_replid are one 40-hex node identity, immutable for the process life); shape client-parseable

      COMMAND

      • registry is the M0+M1 surface, not the full Redis set
      • registry size differs by design
      • flags/acl detail differs; arity+keyspec verified in inf-wire
      • docs payload not implemented (honest empty map)

      OBJECT

      • no LRU clock until the eviction engine (M1); honest 0
      • popularity scale differs: CMS Morris estimate vs Redis log counter

      DEBUG

      • DEBUG JMAP is removed in Redis 8; InfinityDB accepts it and answers +OK without doing anything (DEBUG SLEEP and DEBUG OBJECT are served, DEBUG SET-ACTIVE-EXPIRE is accepted and ignored, and any other subcommand answers an error: see the DEBUG row)
      • value-address/serialized-length fields are engine-internal

      PEXPIRETIME

      • deadlines ≥ ~34.8 years clamp to the u40 record bound — the read-back reports the bound, not Redis's i64 instant

      CONFIG

      • InfinityDB returns the typed M1 key subset
      • error detail text differs; both reject
      • error text shape differs slightly

      CLIENT

      • connection ids are engine-internal (cell<<48|seq, ≥ 1, never reused)
      • addr/fd/timing fields differ; field vocabulary matches

      LOLWUT

      • version art differs by design

      PUBSUB

      • sharded pub/sub (SSUBSCRIBE family) is the recorded M3 cut line

      INF.NS

      • InfinityDB extension
      • InfinityDB extension; durable live since M2 (node tier — the planeless compat candidate answers its documented no-runtime error)
      • InfinityDB extension (M2): named-namespace selection, SELECT-class conn state; durable-mode deviations documented
      • InfinityDB extension (M4): MEM-BUDGET declares a durable-tiered namespace; the planeless compat candidate answers its documented no-runtime error
      • InfinityDB extension (M4): per-namespace hot-reload; CreateOnly keys (TIER-IO-MODE, COLD-READ-QD) refuse typed

      INF.CKPT

      • InfinityDB extension (M2): checkpoint trigger; the planeless compat candidate answers its documented no-durable-plane error

      BGSAVE

      • maps onto INF.CKPT (M2): fuzzy checkpoint, no fork, no RDB file; reply byte-identical on durable nodes; the planeless candidate answers its documented error (node_e2e pins the live reply)

      LASTSAVE

      • M2: newest durable MANIFEST publication time this cell has observed (it can trail the board by up to two bounded sweeps, except after a WAIT on the same cell); 0 before the first save vs Redis's process-start time; the planeless candidate answers its documented error
