      Operate/Observability

      Observability

      What the node tells you, and when: how it boots and loads, what recovery repairs and what it refuses, the two runtime fail-stops, the fields in INFO persistence, and the honest list of what this alpha does not do.

      Available · alpha

      Boot, step by step

      A node started with --data-dir boots in a fixed order: the namespace catalog loads first, then every cell recovers its own shard, independently and in parallel: MANIFEST, the named checkpoint, then the log tail. Recovery time follows the largest shard, not the sum.

      • The node accepts connections from the start, behind a gate. While any cell is still replaying, gated commands receive the exact Redis reply -LOADING Redis is loading the dataset in memory. Clients never see a half-recovered keyspace.
      • The exempt set is Redis's, captured from a live instance: HELLO, ECHO, QUIT, SELECT, INFO, COMMAND, CONFIG, CLIENT, DEBUG, the subscribe family, PUBLISH, PUBSUB and LASTSAVE. PING is gated, because it is in Redis.
      • Progress is visible the whole time in INFO persistence, and stderr narrates each cell. The node is ready when it prints control: recovery complete.

      What recovery repairs

      Damage that is provably inside the defined crash window is repaired, and always counted:

      • A torn final frame, detected by its checksum, is truncated, and replay resumes behind it. That is what a power cut mid-write looks like.
      • A gap that was never fsync-covered, in the unsynced tail or in a segment whose seal never completed. Every frame carries an epoch, a sequence number and the watermark at seal time under its checksum, so recovery can prove nothing at or past the gap was ever acknowledged, and truncate there.
      • Leftover frames from a discarded life of the log, which the epoch stamp identifies, so discarded data never resurrects.
      • Leftovers of interrupted maintenance, such as stale segments and orphaned checkpoint stagings, are collected at boot.

      What recovery refuses

      Damage that could hide lost acknowledged data stops the boot with the evidence named:

      • A surviving frame that attests fsync coverage past the point where valid data ends: the log itself proves the disk dropped bytes that were acknowledged.
      • A MANIFEST that names missing or corrupt state, or a log whose valid data ends below the position the MANIFEST replays from.
      • An unknown record type or flag inside a valid frame, or a frame-format downgrade that no honest writer can produce.

      A refusal is one line on stderr naming the cell and the evidence. Here cell 2's log ends below the position its MANIFEST starts replay from:

      stderr · scroll →
      infinityd: cell 2 boot failed (fail-stop): the log's valid data ends at seg-000000:00064000, below the MANIFEST begin-LSN seg-000000:00064028: fsync-covered bytes are missing — refusing to start

      The process exits with code 1 and the whole node stops: a half-recovered node must never serve. Treat the volume as suspect, then restore the data directory from a backup, or rebuild the namespace from an upstream source of truth. There is deliberately no --force flag that truncates through the evidence.

      Runtime fail-stops

      • fsync failure. The durability watermark freezes, nothing in the affected batch or after it is acknowledged, and the process exits with code 3.
      • A failed catalog swap after a namespace change was acknowledged is the same class and takes the same exit code.

      A checkpoint I/O failure is narrower: it aborts the checkpoint, never the process. You see it as ckpts_aborted rising, which is worth investigating before the same disk fails an fsync.

      INFO persistence

      Every field below is emitted today. Dashboards built on the Redis shapes keep parsing; the InfinityDB fields carry the durable plane.

      FieldMeaning
      loading1 while any cell is still replaying. The loading_* fields appear only then.
      loading_cells_ready, loading_cellsHow many cells have finished recovery, out of how many.
      loading_loaded_bytes, loading_total_bytesBytes replayed and bytes to replay. Totals are file extents including preallocated slack, a disclosed upper bound.
      rdb_bgsave_in_progress, rdb_last_save_timeA checkpoint is streaming; the newest durable MANIFEST, in unix seconds.
      last_durable_lsn, watermark_lag_lsnThe durability watermark, and how far it trails the append cursor.
      pending_log_bytesBytes written or staged but not yet fsync-covered.
      fsyncs_completed, acks_gatedDurability fsyncs completed; always replies that waited on the watermark.
      fsync_latency_p50_us and siblingsThe device's fsync latency, reported as it is: always is storage-bound by definition.
      fsync_group_p50, fsync_group_p99Records covered per fsync: the group-commit shape.
      ckpts_completed, ckpts_aborted, ckpt_age_sCheckpoints finished and aborted, and the age of the last one.
      segments_truncated, log_segments_liveSegments reclaimed so far, and live now.

      What to watch

      • Grouping. always throughput is group commit. If records per fsync collapse toward one, read it together with the device's fsync latency.
      • Watermark lag. Sustained growth in watermark_lag_lsn or pending_log_bytes means the device is not absorbing the offered write rate. Backpressure is explicit: you see refusals, never unbounded memory growth.
      • Reclamation. log_segments_live and ckpt_age_s stay bounded in steady state. If they climb, check ckpts_aborted for the disk trouble behind it.

      The alpha boundary

      • Single node. No replication, no cluster, no failover until M9. always survives any crash of this node, not the loss of its disk.
      • No authentication or TLS. Bind-address control and AUTH arrive before the first public tag, TLS and ACLs with M7.
      • Strings, keys, expiry, pub/sub and JSON documents. No hashes, lists, sets or sorted sets until M5, no transactions or Lua until M6, no streams until M7. The compatibility matrix is exact.
      • Beyond RAM for strings only. A tiered namespace keeps string values without expiry on disk; JSON documents stay in memory until the last phase of M4.
      • Durability is opt-in. A fresh node persists nothing until you create a durable namespace and bind connections to it.
      • Linux with io_uring is the deployment target. macOS builds run for development only.
