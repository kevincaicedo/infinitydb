Evidence

How we benchmark

Every performance number InfinityDB publishes was produced by a process designed to make lying hard — to you, and to ourselves. This page is that process, end to end: the harnesses, the environment rules, the replicate discipline, the instrument checks, and finally the numbers themselves — each one carrying its ledger row and its disclosures.

The rule that governs everything

Project law L10: claims follow evidence. Every number or comparative statement in public copy must have a row marked Allowed in docs/claim-ledger.md, citing a committed artifact. Rows carry one of five statuses — Allowed, Narrowed (a weaker wording is allowed; the original is not), Evidence-pending, Rejected, or bound to a named blocker — and are re-validated per release: a row whose artifact was not re-run in the release campaign reverts to Evidence-pending for that announcement. This website is scanned in CI against the ledger; an uncovered number fails the build. Targets never appear as numbers anywhere — a target dressed as a result is the exact failure mode this project was restarted to kill.

Two harnesses, no silent substitution

inf-bench is the in-house gate harness: it drives the milestone gate workloads (eviction storms, TTL mixes, checkpoint-under-load, crash/recovery cycles, YCSB-style tiered rows) that generic load generators cannot express, and it proves the gates. Because it is ours, its rows are always labeled inf-bench — an in-house harness is a conflict of interest that must be visible.

inf-compare is the comparative harness, and it is deliberately zero-dependency about the interesting part: the load is generated by independent, third-party generators — memtier_benchmark and redis-benchmark — never by our own code. Competitors run in the same run on the same box, each with its own best launch configuration, recorded verbatim in the report. A comparative number without the competitor in the run does not exist. The two generators cross-check each other on every engine/workload pair, and the report flags its own divergences rather than quoting the friendlier one.

The current binding comparative report is published verbatim: the campaign report, rendered by a generator that refuses any report not stamped citation-grade.

What makes a run valid

A run that fails any of these is invalid for claims — not discounted, not caveated: invalid, and labeled so in the artifact.

  • Environment check, mechanically enforced. inf-bench env-check must pass before a binding run starts: clean git tree, performance governor and EPP, turbo off, zero thermal-throttle counters. The harness refuses to run otherwise (a --unsafe-env escape records a permanently non-citable dev run).
  • Placement is pinned and disclosed. Server cells on named P-cores, the load generator on a disjoint CPU set, both recorded in the report header.
  • Replicates with medians. Binding rows run 3–6 replicates; leg medians decide, per-replicate values are committed. Relative spread is reported, and a row whose spread swamps its threshold gets a disposition note instead of a verdict.
  • Tripwires bind per run. Batching metrics (sqes/submit and friends) are recorded in every row; a red tripwire invalidates the row by definition — the number might be flattering, and it still dies.
  • Generator saturation is dispositioned. If the load generator itself is the ceiling, the row is labeled generator-limited and absolute numbers from it are not quoted — only deltas at fixed generator config.
  • Box and tier are named. Development-box numbers can never back a public claim. The reference box (i7-13700KF, consumer Gen3 DRAM-less NVMe — the device class is itself a disclosure) is where binding rows run; device-bound rows that need better hardware are dispositioned Evidence-pending, not rounded up.

A/B runs: the crossover instrument

Regression gates compare two binaries with interleaved ABBA legs — and the instrument itself is audited. Our week-4 M4 risk gate produced a tail-latency reading that followed the harness slot, not the binary: a same-binary A/A control reproduced the exact failing signature with identical binaries. The fix is structural: servers respawn fresh per replicate, the binary↔slot assignment alternates every replicate, and legs run in spawn order — slot and load-order bias alternate sign against the binary and cancel in the leg medians over an even replicate count.

Two consequences worth naming. First, every binary in a binding A/B is fingerprinted into the report, and baselines are rebuilt from a pinned commit whose fingerprint must reproduce byte-exact — a baseline you cannot reproduce is not a baseline. Second, the same-binary A/A control is a standing part of the protocol: it measures the instrument’s own noise floor, and a reading inside that floor is recorded as inconclusive at instrument resolution — claimed by neither side. Tail percentiles come from log-scaled histograms whose buckets are a few percent wide; a one-bucket delta cannot adjudicate a one-percent threshold, and we say so instead of picking the flattering interpretation.

The tiered rule: split percentiles, always

Beyond-RAM workloads (M4) serve two populations: memory hits in microseconds and cold reads that touch NVMe. A blended p99 over that bimodal distribution is a lie by construction — it reports a number no request actually experiences and hides the cold tail entirely. The reporting contract is fixed before the first public tiered number exists: memory-hit and cold-read percentiles are published separately, always; the combined client histogram is context, never the headline.

What you will not find here, and why

The absences are part of the method. Each one is a ledger row that has not earned Allowed status, and each names what is missing:

  • Absolute always-mode write rates. The mechanism is proven (one durability fsync in flight, collecting every arrival during the flush), but the absolute number is owned by the flush latency of a better device class than our Gen3 DRAM-less reference NVMe. Evidence-pending; the mechanism story is citable, the number is not.
  • The everysec cost figure. A previous campaign narrowed it to a citable range; the current campaign’s re-read did not reproduce it — the same binary read dramatically better on a RAM disk the same night, so the shift belongs to the reference SSD’s current state, not the engine. Per the re-validation rule the row reverted to Evidence-pending and the number came off this page — that is the ledger working, not a gap in it.
  • Absolute tail-latency claims. The reference device itself stalls under sustained write load with checkpoints off — the control run proves the excursions belong to the device class, so an absolute p99.9 claim would be a claim about our SSD, not our engine. Narrowed to relative wordings.
  • Tiered-storage numbers (M4). The harness, the split-percentile contract, and the gate table exist; the binding campaign is in progress. Until its rows are signed, no cold-read or beyond-RAM number appears anywhere — and when they do, cold-read tail rows will carry the Gen3 device disclosure explicitly.
  • Document wire ratios (reads vs GET, writes vs SET). Measured at dev tier, on the gate line; the reference-box campaign owns the verdict. Evidence-pending — quoting the dev numbers would be exactly the shortcut the ledger exists to prevent.
Reproduce it: every artifact path above is committed in the repository, raw generator output included. The harnesses are in-tree (bins/inf-bench, bins/inf-compare), the environment checker is inf-bench env-check, and the comparative report renders from its artifact by generator — read the current binding report.
