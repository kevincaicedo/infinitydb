Concepts

Namespaces & durability

Durability in InfinityDB is a property of the namespace, not the server. One node simultaneously serves a cache and a system of record — the difference is which namespace a key lives in. This page states the semantics exactly: what an ack means, what each mode can lose, and how the node behaves after a crash.

Namespaces

A namespace is a logical keyspace with its own durability class, eviction policy, and memory budget. Redis SELECT 0..15 maps to default namespaces; named namespaces are created with INF.NS:

INF.NS CREATE cache    MODE memory   EVICTION allkeys-lfu MAXMEMORY 16gb
INF.NS CREATE ledger   MODE durable  FSYNC always
INF.NS CREATE sessions MODE durable  FSYNC everysec

A memory namespace never touches the log — not “rarely,” never: memory-only workloads append zero log records, which is verified by a report-enforced check in the benchmark harness. topic namespaces (retention instead of eviction, the queue substrate) arrive at M7.

Durability classes

Per namespace, exactly as the engine implements them:

ModeAck pointMechanismLoss window on crash
memory on apply no log everything (cache semantics)
everysec on apply group commit each reactor loop; fsync on a one-second timer (and on segment seal) at most the last second of acknowledged writes
always after fsync the response suspends on the durability watermark; group commit batches all concurrent always writers into one fsync zero (single node) — an acknowledged write survives any crash
wait-replica M9 after R replicas ack watermark = replicated LSN zero across node loss (roadmap — not shipped)

Two consequences worth internalizing:

  • An always ack is a durability fact, not a courtesy. The mutation applies immediately, but the client’s reply is gated: the command future suspends until the group-commit fsync covering its log position completes. Throughput comes from grouping — every concurrent writer shares one fsync — and the fsync latency histogram is reported honestly in INFO persistence, because always is storage-bound by definition.
  • everysec is a real window, stated plainly. Writes are acknowledged on apply and the log is fsynced on a one-second timer, so a power cut can lose up to the last second of acknowledged writes in that namespace. If that window is unacceptable, use always.

fsync failure is fail-stop

If the device reports an fsync failure, InfinityDB does not retry, degrade, or pretend: the durability watermark freezes forever (no further ack can be issued against unverified storage) and the process exits with a dedicated code (EXIT_DURABLE_FAILSTOP). This is the PostgreSQL-fsyncgate lesson, enforced mechanically — a repo script audits that fsync-error types can only appear at allowlisted fail-stop sites, and a child-process test proves the affected batch is never acknowledged.

Checkpoints — no fork, no stop-the-world

Checkpoints replace the BGREWRITEAOF-style rewrite. A checkpoint is a fuzzy snapshot taken by the owning cell in bounded background slices: the live index and records stream incrementally to a .ick file (records mutated mid-checkpoint are simply re-covered by the log tail), then a MANIFEST atomically names the new recovery unit (write-new + fsync + rename + directory-fsync) and older log segments are truncated. Properties:

  • No fork(), no copy-on-write page games, no doubled memory during a rewrite — the cell streams its own memory at its own pace, paced to avoid dirty-page stalls.
  • A MANIFEST is published only once the durability watermark covers the checkpoint’s starting position — a checkpoint can never name state the log hasn’t made durable.
  • Checkpoint I/O failure aborts the checkpoint, never the process — nothing was acknowledged against it and the log stays authoritative.
  • Operator surface: INF.CKPT [CELL k] [WAIT]; BGSAVE maps onto it (reply byte-identical, no RDB file); LASTSAVE reports the newest durable MANIFEST publication.

Recovery

Recovery is per cell and parallel: each cell loads its named checkpoint (a materialized log prefix in the same record format), then replays its log tail from the checkpoint’s position. There is no global log sequence number and no merge step — cells recover independently.

  • While loading, the node answers exactly like Redis does: non-exempt commands receive -LOADING Redis is loading the dataset in memory (the exempt set is pinned to observed Redis behavior). Loading progress is visible in INFO persistence. The gate is node-scoped: a recovered cell still answers -LOADING while a peer replays.
  • Torn tails are expected physics: a torn final batch frame (detected by CRC) is truncated, and replay resumes cleanly behind it — the defined crash window. Since frame format v2 (ADR-0031), every frame carries an epoch, a sequence number, and the durability watermark at seal time under its CRC, so recovery can also prove when a crash-window gap in the un-synced tail was never fsync-covered: those gaps truncate too, and the discarded frames are counted in the recovery stats, never silent.
  • Everything else is a refusal, not a guess. A surviving frame attesting fsync coverage past the point where valid data ends (the log itself proving the disk lost covered bytes), corruption or residue inside sealed segments, a MANIFEST that names a checkpoint or segment that is missing or corrupt, an unknown record type or flag, a frame-format downgrade signature — each is a named error and the boot fail-stops. InfinityDB never silently skips records and never falls back to “replay whatever we can find,” because a database that boots with quietly missing acknowledged data is worse than one that refuses and says why.
What a refusal means for you: a refused boot names the corruption class and the file. It means the on-disk state failed an integrity check that could have hidden lost data. The simulation evidence below audits these refusals: in the sweep, every refusal was legal (the fault genuinely destroyed named state) — refusals are not false alarms, and they are rare; frame format v2’s per-frame attestations narrowed them further by design (ADR-0031), with the §8.2 promises unchanged. The operator’s view — the exact error shape, exit codes, and what to do next — is on the operations page.

Environment for the measured rows: the project’s designated reference box (i7-13700KF, pinned P-cores, performance governor, consumer Gen3 DRAM-less NVMe — the device class is disclosed because it matters).

Deterministic durability testing (ledger C12). “Durability is deterministically tested: 10,000 simulated power-cut/disk-fault seeds, zero durability-oracle violations — every always-acked write survives, everysec loses at most one second (simulated time); every seed replays byte-identically — and on the frame-v2 tree, zero recovery refusals across the same 10,000 seeds.” (Frame format v2 retired the earlier legally-refusing recovery class; the historical numbers live in the artifacts.) artifact: infinitydb/.artifacts/m2/dst-sweep-10k-s22-20260705/ · m2.5/s12-frame-seq-20260709/
Crash matrix (ledger C13). “The crash matrix — 8 named fault points × fsync policies × workloads, kill-and-recover with digest verification — is green at 256 seeds per combination; fsync failure is fail-stop.” artifact: crash-matrix run 2026-07-05 · tests/crash-matrix/m2.toml
Cold-boot recovery (ledger C14). “A 10 GB node (8 cells) cold-boots to serving in under 10 seconds on the reference box (9.8 s, cold page cache, 3 replicates < 1% spread).” Measured 9.8 s against a 15 s gate; Gen3 DRAM-less device named. artifact: infinitydb/.artifacts/m2/parallel-boot-cold-20260705/
Memory namespaces pay zero for durability (ledger C15). “Memory namespaces pay zero for durability: A/B vs the pre-durability build shows ≤ 1% on every gate mix (worst 0.63%, p99.9 same-bucket-or-better), and memory-only runs append zero log records (report-enforced).” artifact: infinitydb/.artifacts/m2/1783232863-gate-run/
Checkpoints are fork-free and memory-flat (ledger C16). “Checkpoints are fork-free and memory-flat: continuous checkpoint cycling under a saturating durable write mix costs ≤ 15 MiB of peak RSS vs a no-checkpoint control (a fork/COW rewrite would cost the dataset).” Measured 14.4 MiB over 176 cycles. artifact: M2-S22 binding report · infinitydb/.artifacts/m2/
Exact memory accounting with the durable plane live (ledger C21). “Memory attribution stays exact with the durable plane live: sum(domains) — including log staging and checkpoint buffers — within 1.1% of RSS on a 1 GB durable fill.” artifact: M2-S22 binding report attribution row
