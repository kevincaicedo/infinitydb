      Status & roadmap

      InfinityDB is built as a sequence of milestones, scoped by capability rather than by date. A milestone is done when its features work from the wire and its exit gates pass, not when a calendar says so.

      An exit gate is a pass or fail check the milestone must meet: a correctness test, a simulation or crash sweep, or a measurement against a stated budget. If one fails, feature work halts until the architecture is fixed. No release has been published yet; the first public tag is cut inside M4, after trust and safety. Milestones after the current one may be reordered.

      M0 · Skeleton

      Shard cells, each a thread with its own io_uring event loop. The fabric: a mesh of single-producer, single-consumer rings with credit-based flow control. The RESP protocol, perfect-hash command dispatch and a minimal store, the benchmark harness that measures exit gates, and the deterministic simulator. It ended in an architecture verdict, not a release.

      M1 · Cache core

      The string, key, expiry and server command families, diffed byte for byte against Redis. A hierarchical timer wheel with budgeted active expiry, all eight eviction policies, namespaces, pub/sub across cells with RESP3 push, the generated compatibility matrix in CI, and a release pipeline not yet used for a release.

      M2 · Durability

      A per-cell append-only log with checksummed frames, segments, group commit and a MANIFEST. Durable namespaces in always and everysec, fuzzy checkpoints, truncation and parallel recovery. A crash matrix and simulated disk faults with planted-bug canaries, including an fsync that lies, that the oracles must catch. Then a hardening pass before the feature train: group-commit and replay work, cross-cell overhead, a comparison harness, fuzzing and soundness audits.

      M3 · JSON documents

      JSON as a first-class value stored as a compact binary tape, a SIMD JSON parser, a JSONPath subset compiled to cached path programs, RedisJSON-compatible JSON.* commands with in-place updates, durable documents through delta log records, and per-document memory accounting.

      M4 · Tiered storage, indexes and the first public alpha

      M4 is in progress. It runs in phases:

      • Tiered storage, done for string values. A per-cell hybrid-log address space: cold reads through io_uring with direct I/O, compaction, large values as blob extents, and per-namespace memory and disk budgets.
      • The write path, done. Barriers chosen by a device probe at first boot, a bounded pipeline of frame writes, a device I/O budget, segment recycling, backpressure instead of errors, and a graceful stop that keeps every acknowledged write.
      • Secondary indexes and a PartiQL subset, in progress. The ordered index, index maintenance and backfill, the predicate VM and the query compiler are built and tested. The command surface, index DDL, queries, EXPLAIN and JSONPath filters, comes next, after the work that bounds and reserves capacity across the engine. See Indexes & PartiQL.
      • Trust and contracts, planned. Bind-address control with a protected default, AUTH and requirepass, an end-to-end request envelope with output, request-size and work limits and typed refusals, and published format and support matrices. The first public tag follows.
      • Documents beyond RAM, planned. Cold document reads and updates, expiry on tiered namespaces, indexes over cold documents, and queries that touch a single cell, a tenant's keys co-located by hash tag.

      M5 · Data types

      Hashes, lists, sets and sorted sets, with sorted sets reusing the ordered index. Size-adaptive encodings, the SCAN family for every type, OBJECT, MEMORY USAGE, keyspace notifications, sharded pub/sub, SLOWLOG and MONITOR.

      M6 · Transactions

      MULTI, EXEC and WATCH, inline on one cell and across cells through deterministic, ordered lock acquisition. A native all-or-nothing transaction, conditional writes on a revision, and Lua scripting with declared keys.

      M7 · Streams & queues

      Topics on the same per-cell log and the Redis Streams surface. Offset consumption, idempotent producers, dead-letter queues, delayed delivery and retention. Client tracking, multi-user ACLs, TLS, RDB import, backup and point-in-time recovery. An agent-memory profile: freshness barriers, fenced worker claims, per-namespace users and work budgets, and adapters for Python and TypeScript agent frameworks. The first beta.

      M8 · Vectors

      Redis-compatible vector sets and native vector collections. Per-cell HNSW with quantization and rescoring, k-NN gathered across cells, filter predicates, and embeddings kept in step with document revisions.

      M9 · Replication & HA

      Per-cell log shipping with state digests, WAIT and read-from-replica, an asynchronous profile and a strong profile over a quorum-replicated log, a metadata-only control plane, fenced failover and a fault harness.

      M10 · Compute & embedded

      WASM reducers that run on the cell that owns their data, with fuel and memory limits and scoped capabilities. An embedded library mode, a shared-memory transport, full ACLs, an audit log and documented extension seams.

      M11 · GA hardening

      No new features: long mixed-workload soaks, broader fuzzing, every public claim measured again, a frozen compatibility matrix and frozen seams, an upgrade path and a third-party security audit. Then 1.0.0.
