      Concepts/The fabric

      The fabric

      Cells never touch each other's memory. When a command needs a key that another cell owns, it crosses the fabric: a full mesh of single-producer, single-consumer rings, paid for in batches and bounded by credits.

      Available · alphaLaw L3

      One ring per directed pair of cells. Requests spend a credit; replies never need one.

      A ring per pair

      A node of N cells builds N × (N − 1) rings, one for each directed pair. Each ring has exactly one producer and one consumer, so it needs no lock. It is a fixed power-of-two array of 64-byte slots, 4,096 slots in infinityd. The producer and the consumer each own a free-running index on its own cache line and keep a cached copy of the other side's index, so the common case touches only local memory. A whole batch is published with one release store and consumed with one release store.

      The fabric is the only way cells talk: no shared tables, no shared queues, no locks on the data plane.

      Batched once per loop

      A message is an encoded operation with an 8-byte header. Up to 62 bytes sit inline in a ring slot; a larger message spills to the heap. Operations toward one destination are packed into an open buffer that seals into a single slot at 2 KiB or 64 operations, so one slot carries many operations and one heap allocation is shared by the whole pack.

      Publishing follows the cell loop. Requests are published at the FABRIC-OUT step near the end of an iteration, and each destination with new work gets one doorbell for the batch. The receiving cell drains at FABRIC-IN, about 1,024 messages per iteration, round-robin over its peers from a rotating start. The replies a drain produced are published as soon as the drain ends, not at the end of the iteration, which shortens the round trip.

      An idle cell parks in the kernel. So that no wakeup is lost, it sets its park flag, issues a full fence and checks its doorbells again before it sleeps. A publisher writes the peer's eventfd only when that flag is set. You can watch the batching: INFO tripwires reports fabric_msgs_per_batch for the cell that served the command.

      When the key is remote

      Routing reads the key's slot from the command table's key specification. If the connection's own cell owns the key, a command on a numbered database runs inline, with no future and no task. If another cell owns it, the command moves to the connection's pump, a per-connection future, and suspends:

      • The pump encodes an Apply operation carrying a token (16 bits of origin cell, 48 bits of sequence), takes a credit and waits on the gate for that token.
      • The owner drains it, runs the command exactly as if a local client had sent it, and replies with the raw RESP bytes, so the reply is identical either way.
      • The origin returns the credit, completes the gate, resumes the pump in the same iteration and appends the reply to the connection's output.

      Replies keep request order. Once a connection defers one command, the commands behind it in the same pipeline are deferred too, so a fast local reply can never overtake an earlier remote one. Suspension is safe because nothing borrowed before it is trusted after it: a resumed command looks up what it needs again.

      Multi-key commands

      Redis Cluster answers CROSSSLOT when a multi-key command names keys in different slots. On InfinityDB's numbered databases those commands work across cells and pay a fabric hop instead. MGET gathers each value from its owner, in key order. DEL, UNLINK, EXISTS and TOUCH send one operation per remote key and sum the results; if any leg fails, the reply is that error, never a partial sum. MSET sends one leg per remote pair.

      redis-cli · scroll →
      127.0.0.1:6379> MSET user:1 ada user:2 grace
OK
127.0.0.1:6379> MGET user:1 user:2 user:3
1) "ada"
2) "grace"
3) (nil)

      Two limits are stated plainly. Multi-key writes that span cells are not atomic across cells: another client can see some legs applied and not others. And on a named namespace, a multi-key command whose keys live on more than one cell is refused, JSON.MGET excepted. Keys that share a hash tag, such as {u42}, always land on one cell. See Strings & keys.

      Credits and backpressure

      BoundDefaultWhen crossed
      Unanswered data operations toward one peer1,024 creditsthe sender waits for a credit to return
      Remote operations in flight per connection32the pump stops dispatching until replies arrive
      Pending replies per connection256the pump stops dispatching until replies drain
      Queued commands per connection1,024, resume at 64the cell stops receiving; TCP pushes back on the client
      Fabric drain per iterationabout 1,024 messagesthe rest wait for the next iteration

      Pressure travels back to the client instead of into a growing queue. A saturated owner returns credits slowly, the origin's pumps stop dispatching, queued commands reach their cap and the cell disarms the connection's receive. TCP flow control does the rest.

      Replies need no credit, and each ring holds at least twice the credit count, so a reply can always be sent. The drain never blocks and never sends. Together these remove the cycle in which two cells wait on each other, so the fabric cannot deadlock.

      How the ring is checked

      The ring is the only unsafe code in inf-fabric, and each block is listed with its argument in the crate's SAFETY.md. Indices use release and acquire ordering only, never SeqCst. Loom model-checks publish, consume, wrap-around, full, empty and the stale-cache path across two threads, and Miri runs the ring's tests under strict provenance. The fabric codec's decoder is total, bounded and fuzzed. If you change inf-fabric, run the model check:

      shell · scroll →
      $ just loom

      In the simulator the whole mesh runs on one thread, so a failing cross-cell interleaving replays from its seed.

      L3
      Batch every boundary.

      A fabric hop is a boundary, like a syscall or an fsync, and it is paid once per batch: many operations per slot, one release store per batch, one doorbell per destination per iteration.
