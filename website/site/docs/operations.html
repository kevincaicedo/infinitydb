Docs / Operations

Operations

What the node does after a crash, exactly which commands answer while it loads, what a refusal to boot means (and why there is no --force flag), what to watch in INFO persistence, and the honest list of what this alpha does not do. The semantic contract behind all of it — ack points and loss windows — is on the namespaces & durability page.

Recovery, step by step

A node started with --data-dir boots in a fixed order: the namespace catalog (META) loads first, then every cell recovers its own shard independently and in parallel — MANIFEST → the named checkpoint → log tail replay from the checkpoint’s position. There is no global log and no merge step; recovery time scales with the largest shard, not the sum.

  • The node serves from its first moment — but behind a gate. While any cell is still replaying, gated commands receive the exact Redis reply: -LOADING Redis is loading the dataset in memory.
  • The gate is node-scoped: a cell that finished replaying still answers -LOADING while a peer replays. Clients never observe a half-recovered keyspace.
  • Which commands answer during load (the exempt set is pinned to observed Redis 8.0.5 behavior, captured on a live instance, not copied from docs): HELLO, ECHO, QUIT, SELECT, INFO, COMMAND, CONFIG, CLIENT, DEBUG, SUBSCRIBE, UNSUBSCRIBE, PSUBSCRIBE, PUNSUBSCRIBE, PUBLISH, PUBSUB, LASTSAVE. Notably PING is gated — because it is in Redis. Unknown commands get the unknown-command error first, matching Redis resolution order.
  • Progress is visible the whole time: INFO persistence (exempt from the gate) reports the loading_* fields below, and the node’s stderr narrates per-cell progress.

What recovery repairs, and what it refuses

Recovery draws one line, and draws it loudly. On one side: damage that is provably inside the defined crash window, repaired silently but always counted. On the other: damage that could hide lost acknowledged data, refused with a named error.

Repaired and counted

  • A torn final batch frame (detected by CRC) is truncated and replay resumes cleanly behind it. This is the expected physics of a power cut mid-write.
  • A provably un-covered gap in the un-synced tail. Since frame format v2 (ADR-0031), every frame carries an epoch, a sequence number, and the durability watermark at seal time under its CRC. When a crash leaves a gap followed by surviving frames, recovery reads those attestations: if no surviving frame attests fsync coverage at or beyond the gap, nothing in it was ever acknowledged as durable — the tail truncates at the gap and the discarded frames are counted in the recovery stats, never silent.
  • Residue of a discarded log life: every frame’s epoch stamp names which life of the log wrote it, so replay ends cleanly where an older life’s leftover frames begin — discarded data can never resurrect into the live prefix (counted, like every repair).
  • Leftovers of interrupted maintenance — stale below-floor segments, orphaned .ick.new checkpoint stagings — are garbage-collected at boot.

Refused, with the evidence named

  • A surviving frame that attests fsync coverage past the point where valid data ends — the log itself proves the disk lost bytes that had been fsynced and acknowledged.
  • Interior damage in sealed territory: corruption or gaps inside a sealed segment, or any validating frame beyond a sealed segment’s recorded end — sealed segments were fully covered by their seal fsync, so damage there is covered loss.
  • A MANIFEST that names missing or corrupt state — a checkpoint or segment that is absent, or a log whose valid data ends below the MANIFEST’s begin position. Everything a MANIFEST names was durable at publication; its absence means the disk lied.
  • An unknown record type or flag inside a CRC-valid frame — corruption-or-bug; replay refuses rather than skips.
  • A v1-format frame beyond a gap — pre-v2 frames carry no attestation, so the conservative rule holds for them: refuse rather than guess. This class ages out as v1 frames leave the retained log.
  • A frame-format downgrade signature (a v1 frame after a v2 frame) — unreachable by any honest writer.

A refusal looks like this on stderr (the corruption class, the file, the offsets, and the evidence are always named):

infinityd: cell 2 recovery failed (fail-stop, §8.4): log corruption in seg-000004
at 0x3f2c0: <what the bytes looked like>; a validating frame follows at seg-000004
offset 0x40000 — interior data would be lost by truncation, refusing to start (§8.4)

The process exits with code 1 and the whole node stops — a half-recovered node must never serve.

What a refusal means for you: the on-disk state failed an integrity check that could have hidden lost acknowledged writes. This is disk-integrity evidence, not an InfinityDB bug to work around: in the project’s simulation sweeps every refusal is audited, and refusals fire only when the injected fault genuinely destroyed named state. Treat the volume as suspect. Restore the data directory from a backup or snapshot, or rebuild the namespace from an upstream source of truth. What is deliberately not offered: a --force or “repair” flag that truncates through the evidence — a database that boots with quietly missing acknowledged data is worse than one that refuses and says why. Refusals are also rare by design: frame format v2’s per-frame attestations let recovery prove most crash-window gaps harmless and truncate them, so what remains refusing is the class where the log proves the disk dropped covered bytes.

Runtime fail-stops

Two conditions stop a running node on purpose. Both mean the storage stack broke a promise; neither is recoverable by retrying.

  • fsync failure (the PostgreSQL-fsyncgate lesson): if the device reports an fsync error, the durability watermark freezes forever — zero acknowledgements are issued for the affected batch or anything after it — and the process exits with code 3 (EXIT_DURABLE_FAILSTOP). This is enforced mechanically: a repo script audits that fsync-error types can only appear at allowlisted fail-stop sites, and a child-process test proves the affected batch is never acknowledged.
  • Namespace catalog swap failure: a failed META swap after a DDL was acknowledged is the same class and takes the same exit code 3.

Checkpoint I/O failure is deliberately narrower: it aborts the checkpoint, never the process — nothing was acknowledged against an in-flight checkpoint and the log stays authoritative. You will see it as ckpts_aborted ticking up, which is worth investigating before the same disk fails an fsync.

What to actually watch

Field-level tripwires, as operator concepts — the same signals the project’s own benchmark gates enforce mechanically:

  • Grouping ratio (fsync_group_p50): always throughput is group commit — many concurrent writers sharing one fsync. If the group size collapses toward one record per fsync, throughput degrades toward the device’s raw fsync rate. Read it together with the fsync latency percentiles: a slow device with healthy grouping and a fast device with collapsed grouping look identical from the outside.
  • Watermark lag (watermark_lag_lsn, pending_log_bytes): sustained growth means the device is not absorbing the offered durable write rate. InfinityDB’s backpressure is bounded and explicit — you will see admission refusals, never unbounded memory growth.
  • Reclamation health (log_segments_live, ckpt_age_s): both should stay bounded in steady state. A climbing segment count or an ever-aging checkpoint means truncation is not running — check ckpts_aborted and manifests_aborted for the disk trouble behind it.
  • Batching health (a concept from the project’s gate runs): the engine batches every boundary — syscalls per iteration, submissions per ring flush, log writes per loop. The in-repo benchmark harness enforces these as report-level tripwires; a deployment that suspects a pathology should reproduce with inf-bench rather than eyeball raw counters.

Known limitations — the alpha boundary

The honest list. Every “until Mn” label refers to the roadmap; nothing below is hidden behind marketing.

  • Single node. No replication, no cluster, no failover. The wait-replica durability class (zero loss across node failure) is M9 — not shipped. Single-node always means: survives any crash of this node; it does not survive the disk itself dying.
  • No AUTH, no ACL, no TLS until M7. Bind to localhost or a trusted private network. Docker users: the io_uring seccomp profile is required; it is a syscall filter, not an authentication substitute.
  • 68 commands. Strings, keys and expiry, SCAN, pub/sub, INFO/CONFIG/CLIENT admin, and the checkpoint surface — the exact per-command status is the generated compatibility matrix. No collections yet (lists, hashes, sets, sorted sets — M5), no MULTI/EXEC transactions or Lua (M6), JSON documents arrive at M3, streams at M7.
  • Bounded record sizes: keys up to 255 bytes, values up to 16 MiB − 1 (the inline record bound — out-of-line blob storage is a later roadmap item). Oversized operations are refused at the command layer with an error, never truncated.
  • Datasets are RAM-resident. Durable namespaces are recovered into memory; larger-than-RAM tiered storage is M4.
  • Durability is opt-in per namespace. The default namespaces behind SELECT 0..15 are memory mode — a fresh node persists nothing until you create a durable namespace with INF.NS. This is the single most important operator fact on this page; the durability page is the contract.
  • Operational surface is deliberately small: flags plus a CONFIG subset; no config file; no keyspace notifications, SLOWLOG, or MONITOR yet; no shutdown handshake (a stop is a crash, within the stated loss windows).
  • Linux with io_uring is the deployment target. macOS builds run for development only (kqueue) and are not a performance or deployment target.
