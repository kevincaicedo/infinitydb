Architecture

A condensed tour of the internals. The full version — and the first document a new engineer reads — is infinitydb/ARCHITECTURE.md in the repository; the architectural authority with laws, gates, and the roadmap is docs/infinity-master-plan.md.

The problem

Modern applications run a zoo: Redis for caching and real-time structures, DynamoDB-class stores for durable documents, Kafka or RabbitMQ for queues and events, a vector database for AI retrieval — plus the glue, the double writes, and the cross-system consistency bugs between them. Each system is operated, secured, monitored, and paid for separately, and the data they share is copied between them over networks.

InfinityDB is one engine for those workloads: a key/value engine kernel, Redis-compatible on the wire, with each workload arriving as a projection of the same core rather than a bolted-on subsystem. Workloads are consequences, not targets: anything that would require new kernel semantics rather than a new engine on existing seams is out of scope until a law amendment says otherwise.

The shape: one core, one shard, one owner

One node is one process, infinityd. It pins one shard cell per data core; each cell is a complete miniature database — an io_uring reactor, a SIMD RESP parser, a single-threaded command executor, a slice of the keyspace with its index and record arena, a log writer, and an allocator. One additional control thread runs the slow plane (config, topology, stats, checkpoint scheduling) and is never on the data path.

The keyspace is partitioned by the same 16,384-slot space as Redis Cluster, assigned to cells in contiguous ranges — hash tags co-locate keys exactly as Redis Cluster clients expect, and unlike Redis Cluster, cross-slot operations work: they pay a fabric hop instead of returning CROSSSLOT.

Cells share nothing on the data plane: no locks, no shared atomics, no cross-core cache-line traffic. Persistence, expiry, eviction, memory accounting, and replication all become local, single-threaded problems. The honestly-stated cost is hot keys: a single hot key serializes on one core. Mitigations, in order: a single cell sustains a very large pipelined rate on one key; RESP3 client-side caching (M7) is the protocol-native fix; read-leases are post-1.0 research.

The fabric

When a command on cell A needs a key owned by cell B, it crosses the fabric: a full mesh of lock-free single-producer/single-consumer ring pairs, polled cooperatively, batched, never waking per message, with credit-based flow control so a saturated peer exerts backpressure to the originating client connection instead of queueing unboundedly. The command future suspends until the reply arrives. The fabric is held to the numbers production thread-per-core systems demonstrably achieve — a lesson written in blood: the predecessor project rejected shared-nothing based on a broken fabric experiment that contradicted published production behavior.

The log spine

Every durable fact is an append to a per-cell, per-namespace segmented log, group-committed once per reactor iteration, with the fsync policy chosen per namespace (always / everysec / memory — see durability). Everything else — the hash index, and on the roadmap document trees, secondary indexes, stream offsets, vector graphs — is a rebuildable projection over that log. Checkpoints are fuzzy snapshots streamed by the owning cell (no fork, no stop-the-world); recovery is checkpoint + parallel per-cell replay. There is no global LSN: each cell replays independently.

This is why the feature set can be broad while the trusted computing base stays small: there is one durability mechanism to make correct, not five. A cache is the log with durability off; a queue (M7) is the log read forward by consumer groups; a replica (M9) is the log shipped to a follower.

The reactor: batch every boundary

Syscalls, fabric hops, fsyncs, and cache misses are paid per batch, never per operation. Every SQE an iteration produces goes out in a single io_uring_enter; the log writer seals one batch frame per iteration; all concurrent always writers share one group-commit fsync; index probes are prefetched a batch at a time. The batching metrics (sqes/submit, commands per iteration, acks per fsync) are always-on tripwires with CI gates — a benchmark run with red tripwires is invalid for claims by definition.

Commands are resumable state machines

Commands compile to !Send futures on a minimal cell-local executor — no work stealing, no atomic wakers, no global runtime. The local fast path completes synchronously inside poll and pays essentially nothing for the capability; suspension is reserved for the moments that need it: a remote key, a cold read (M4), a durability-gated ack, a blocking op. Background work (expiry, eviction, checkpoints) runs in deficit-weighted budgeted slices so tail latency is protected by construction rather than by retrofitted fairness passes.

Determinism is a feature

Time, randomness, disk, network, and fabric effects are injected behind runtime traits. Consequently the entire node — all cells, fabric, log, recovery — runs deterministically on one thread inside the simulator, FoundationDB/TigerBeetle-style: simulated disks tear writes and lie about fsync, power cuts land at chosen log positions, and every failure is a seed that replays byte-identically. Invariant oracles (per-key linearizability, durability-watermark honesty, accounting reconciliation) run continuously inside the sim, and a nightly fleet burns simulated time at scale. The simulator’s authority is guarded mechanically: cell code cannot name tokio, locks, thread::sleep, ambient clocks, or ambient randomness — a denylist script enforces it.

Memory is the product

Records are variable-size and packed; the index is a compact Swiss-style table; every allocation belongs to a named per-cell domain counted at the allocation site, and sum(domains) diverging from process RSS beyond a bound fails CI. Bytes/key and RSS-vs-Redis are release gates, not dashboards — the predecessor shipped multiples of Redis memory and could not say where it went; that failure mode is now impossible to hide.

A kernel with seams

Every engine capability registers through a versioned seam: the command registry, record-type registry, index projections, fabric opcodes, triggers, transports. First-party engines (documents, query, streams, vectors, compute) are required to use these seams — the Linux-driver discipline: drivers prove the driver API — and a mechanical dependency-DAG check makes bypassing them a build failure. That is what makes slim builds real (a cache-only binary contains zero document/query/vector code) and what the post-1.0 native extension SDK will stabilize. The compute plane is the same idea aimed at users: WASM reducers (M10) run inside the process on the core that owns their data — fuel-metered, memory-capped, capability-scoped, deterministic.

Safety is layered

unsafe lives only in audited leaf crates (allocator, rings, SIMD), each with a safety inventory and Miri/Loom coverage; everything above is safe Rust. Every byte decoder is fuzzed. Every durability change runs the crash-point matrix. Rust was chosen because the requirements — no GC pauses on a tail-latency-gated data plane, precise layout, invariants as compile errors, !Send futures encoding “this never leaves its core” in the signature — narrow the field to it.

Lineage

The design stands on named shoulders: TigerBeetle (deterministic simulation, assertion discipline, style-guide culture), FoundationDB (DST as the centerpiece of correctness), Seastar/ScyllaDB (shard-per-core, scheduling groups), DragonflyDB (shared-nothing Redis semantics at production scale), Microsoft FASTER (the hybrid-log design behind M4 tiering), Redpanda (thread-per-core Kafka-model storage), simdjson (SIMD parsing), and SpacetimeDB (the in-database reducer model).
