The log is the database — how InfinityDB is being built

InfinityDB wants to be five systems in one process: a Redis-compatible cache, a durable key-value store, a JSON document store, a queue, and a vector index. That is an easy sentence to write and a very easy project to fail at. This post is about the discipline model that is supposed to keep us honest — because the interesting part of this project isn’t the feature list, it’s the process that decides what gets to ship.

We already failed once, on purpose the second time

InfinityDB is a full restart of a predecessor called Vortex, and Vortex’s post-mortem is constitutional — it is written into the project’s master plan, root cause by root cause, and every design law traces back to one of its failures.

Vortex was not lazy work. It had a SIMD RESP parser, a carefully engineered hash table, typed durability errors with crash-point testing, and a genuinely large concurrency experiment behind its central architectural choice. It still failed: throughput landed at roughly parity with Redis where the targets said multiples, memory came in at multiples of Redis where the target said less, and tail latency had cliffs orders of magnitude over budget. The components were excellent. The system was wrong.

The post-mortem found the pattern: every major decision had been validated in isolation — a lock model proven in a lab that measured only the data plane, while the real server spent most of its CPU in I/O completions the lab never saw; an architecture-defining experiment whose result contradicted the published behavior of production systems, and nobody checked. Features were built for months on a foundation whose end-to-end behavior had never been proven.

So the restart inverted the order. The first milestone of InfinityDB, M0, contained no features. It was an end-to-end skeleton — reactor, fabric, wire protocol, minimal store, benchmark harness, simulator — with hard numeric gates, and the rule that no feature work would begin until the architecture proved itself under the wire protocol. That rule has teeth: an M0 gate that came in red is still formally open today, dispositioned in a public architecture decision record and carried into the current milestone’s performance work — not narrowed, not forgotten.

One primitive

The technical thesis is a single sentence: all five workloads are projections of one primitive — a per-core, append-only, segmented log.

A cache is the log with durability off. A durable KV store is the log plus an in-memory index plus checkpoints. A queue is the log read forward by consumer groups. A replica is the log shipped to a follower. Change data capture is the log handed to a subscriber. Point-in-time recovery is the log replayed to a position.

This is not an aesthetic preference; it is a correctness budget. A system that bolts a WAL onto a hash map, a queue onto the WAL, and replication onto the queue has three durability mechanisms to make correct, each with its own crash windows and its own bugs. InfinityDB has one. The hash index, the document trees (M3), the secondary indexes (M4.5), the stream offsets (M7), the vector graphs (M8) — all of them are declared, mechanically, to be rebuildable projections over the log. If a projection is wrong, replay rebuilds it. If the log is wrong, nothing else matters, so everything the project has goes into making the log right.

Around that primitive sit eleven design laws — one core/one shard/one owner; batch every boundary; memory is the product; every command is a resumable state machine; determinism is a feature; claims follow evidence, and so on. The laws are not a philosophy page. A pull request that violates one needs the master plan amended first, and two of them are enforced by scripts rather than reviewers: the dependency DAG between crates is checked mechanically (the storage crate cannot see sockets; the wire crate cannot see records), and cell-resident code that names tokio, a mutex, thread::sleep, an ambient clock, or ambient randomness fails the build.

Determinism, or: every failure is a seed

That last denylist exists because of the project’s favorite feature, which is invisible: the entire node — all cells, the fabric, the log, recovery — runs deterministically on one thread inside a simulator, in the FoundationDB/TigerBeetle tradition. Time, randomness, disk, and network are injected effects. Simulated disks lose un-fsynced writes, tear frames, and lie about fsync; power cuts land at chosen log positions; invariant oracles (per-key linearizability, durability-watermark honesty, accounting reconciliation) run continuously inside the simulation.

The payoff is that failure is replayable: the ledger-backed claim is that the simulator produces byte-identical traces from the same seed, and the oracles run nightly. When the nightly fleet’s very first corpus run caught a real defect in pub/sub reply pairing, the failing seed replayed exactly, was fixed, and joined the regression corpus forever. Two more ledger-backed examples of what this buys, both correctness claims with committed artifacts: ten million TTLs across 48 simulated hours fire exactly — zero early, zero missed — and the durability plane survived a sweep of 10,000 simulated power-cut and disk-fault seeds with zero durability-oracle violations: every always-acked write survived, every seed replayed byte-identically. A small, disclosed fraction of those simulated boots refuse to start with a named corruption error — each refusal audited as legal, because the injected fault genuinely destroyed named state. We think a database that refuses loudly beats one that boots quietly wrong, and we test the refusals too.

STOP gates

The roadmap is a train of milestones, each an independently shippable product: cache, then durability, then documents, tiered storage, queries, collections, transactions, streams, vectors, HA, compute. Each milestone ends in STOP gates — hard, numeric, end-to-end acceptance criteria measured on a designated reference machine with a controlled environment. A red gate halts the train. The fix happens at the architecture layer, and if the gate itself was wrong, changing it requires a public architecture decision record with comparator-anchored evidence — never a quiet edit.

This has real consequences. Milestones M1 and M2 produced verdicts, not public releases — their gate campaigns are why there has never been an InfinityDB release tag, even with the cache and durability planes implemented and tested. The current milestone, M2.5, exists specifically to turn M2’s GO verdict into the first public tag (v0.2.0-alpha.1) the hard way: performance debt paid and measured first, soak and simulation campaigns after, evidence closure before announcement. The M2 campaign is also a good advertisement for gates: one of its rows caught a real group-commit defect — the fsync grouping ratio was a fraction of what the architecture promised — which was fixed in-campaign and verified by the same harness that caught it. That is what gates are for. A benchmark suite that only ever says yes is decoration.

The claim ledger, or: why this site has no benchmark numbers

The strangest artifact in the repository, for most visitors, will be docs/claim-ledger.md. Every number or comparative statement in InfinityDB’s public copy — this site included — must have a row there marked Allowed, citing a validated artifact: replicated runs, clean tree, recorded governor and thermals, load-generator saturation checked, competitors in the same run on the same box, flamegraph and memory attribution attached. Development-box numbers can never back a performance claim. Rows are re-validated per release; a stale artifact flips its row back to pending. A claim absent from the ledger does not exist, and this website is scanned against the ledger in CI.

Right now the ledger allows a set of correctness claims — byte-compatibility counts against a pinned Redis oracle, the simulation and crash-matrix results above, recovery behavior — and keeps most throughput and latency rows in Evidence-pending or Narrowed states, several gated on hardware the project has named but not yet run. So the honest answer to “how fast is it?” is: the architecture was built for a specific performance model, the gates that prove it are public, and the numbers will appear when the ledger allows them — not before. If you find that unsatisfying, good — so do we, which is why the current milestone’s whole purpose is closing evidence. What we will not do is publish a target dressed as a result. That is precisely the failure mode this project was restarted to kill.

What ships today, and what’s next

Today InfinityDB is a Redis-compatible in-memory cache (strings, keys, expiry, eviction, pub/sub — per-command status in the generated matrix) plus durable KV namespaces with always/everysec fsync classes, fork-free checkpoints, and parallel recovery. Single node, no auth or TLS yet, early alpha. Next: the first public tag, then JSON documents.

If the discipline model appeals to you more than the feature list — that is the correct reaction, and you should follow the build. Read the master plan. Hold us to it.
