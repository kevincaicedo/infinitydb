Why Vortex failed: a post-mortem in five root causes and eleven laws

Vortex — InfinityDB’s predecessor — was not killed by lack of effort or lack of optimization. It accumulated ~76 KLoC, a SIMD RESP parser, a SwissTable engine, typed AOF with crash-point testing, and a 1,152-run concurrency experiment — and still shipped 1.02–1.32× Redis throughput against a 1.5–2× target, 2–3× Redis memory against a ≤1.5× target, and p99.9 cliffs up to 966 ms under load.

The failure was architectural. This is the honest accounting — five root causes, each answered by a design law that now governs InfinityDB. The same text lives in the project’s master plan as its constitutional §2; nothing here is softened for marketing.

RC-1 — The architecture was chosen by a microbenchmark. The macrobenchmark disagreed.

Vortex’s sharded-lock model scored 98.6/100 in our concurrency lab — measuring the data plane in isolation. Then the flamegraphs of the real server arrived: ~75% of CPU in io_uring completion handling and syscalls, with a measured command batch size of 1.0 — no batching benefit ever materialized. The locks we had spent months optimizing were never the bottleneck. The I/O plane we treated as plumbing was.

LAW DERIVED

The end-to-end system is the unit of validation. No data-structure or concurrency decision is “settled” until the full server proves it under the wire protocol. Milestone 0 of InfinityDB was a performance skeleton with hard STOP gates — before any feature work was allowed to exist.

RC-2 — The shared keyspace turned every subsystem into a cross-cutting concern

Because all reactors mutated one concurrent keyspace, every feature had to thread through global coordination: a global LSN for AOF ordering, per-reactor AOF files with a K-way merge heap on replay, writer-epoch validation, stop-the-world rewrite snapshots — BGREWRITEAOF was permanently disabled — and a memory accounting that never reconciled. The checkpoint sections of the Vortex plan read as a war journal of complexity created by a single decision.

LAW DERIVED

Every byte has exactly one owning core. Persistence, expiry, eviction, accounting, and replication become local, single-threaded problems. The K-way merge, the epoch gates, and the global LSN disappear outright — each cell replays its own log independently and in parallel.

RC-3 — The 64-byte fixed entry traded permanent capacity for hot-path elegance

Cache-line-aligned fixed entries are beautiful in a probe benchmark and ruinous in RSS: 2–3× Redis memory erased the value proposition of a cache server. Memory is not a tuning parameter for this product category. It is the product.

LAW DERIVED

Memory layout is variable-size and compact by default: packed records, a small amortized index slot. Memory gates — absolute bytes per key and RSS versus Redis — are release blockers from the first alpha, with full attribution in every benchmark report.

RC-4 — The experiment that rejected shared-nothing was invalid. Nobody checked it against reality.

Our shared-nothing proof-of-concept measured 25–45 μs per cross-shard hop and scored 19.7/100, locking in the shared-keyspace architecture with apparent scientific authority. But production thread-per-core systems — Seastar/ScyllaDB, Dragonfly, Redpanda — achieve 0.3–2 μs batched cross-core hops. Dragonfly serves on the order of millions of ops per second on uniform random keys; arithmetically impossible if hops cost 25 μs. The POC benchmarked a bad message fabric — wake-per-message, no batching, synchronous request-reply — not the architecture. The “locks are 100,000× cheaper than messaging” argument compared a real lock against a strawman fabric.

LAW DERIVED

Any internal result that contradicts the published behavior of production systems is presumed an implementation artifact until proven otherwise. The InfinityDB fabric has numeric gates that match what the industry demonstrably achieves — and its cross-cell claim today is comparator-anchored, measured with the competitor in the same run.

RC-5 — Features were ordered before architecture proof

Vortex built four phases of features on an unvalidated end-to-end foundation, then spent months retrofitting fairness budgets, backpressure, and admission control. Targets of 6M GET/s were published while the system shipped 1.0×.

LAW DERIVED

Every milestone has STOP gates; failing one halts feature work and the fix happens at the architecture layer. Public claims are governed by the evidence ledger — Allowed | Narrowed | Rejected, never assumed. A target is never published as a result.

What Vortex got right — and we kept

The post-mortem is not a purge. The SIMD RESP parser (6.2 KLoC, measured, portable), the io_uring buffer-lifecycle craftsmanship, the crash-point testing discipline, the Clock + Count-Min-Sketch eviction design, the hierarchical timing wheel, and — above all — the evidence methodology all carry over. That last one was learned at great cost. It is now constitutional.

// THE INVERSION

Vortex proved the team can build fast components; it failed because the components were assembled around an architecture that made batching impossible to win and memory impossible to attribute. InfinityDB inverts the order: one law — one core, one shard, one owner — makes every hard subsystem local. One primitive — the per-cell log — makes durability, queues, replication, and tiering the same mechanism. One discipline — gates before features — makes sure we never again publish a 2× target while shipping 1.02×.
