What a cell is

A cell is one pinned thread running one loop: its own network listener, protocol parser, executor, slice of the keyspace, allocator and log writer. Cells never touch each other's memory. They talk only through the fabric, in batches.

Every cell binds the same port, and the kernel spreads incoming connections across them. A control thread runs the slow plane, such as configuration, statistics and checkpoint scheduling, and is never on the data path.

How a key finds its owner

owner(key) = slot_to_cell[ crc16(hashtag(key)) % 16384 ]

The keyspace uses the same 16,384 slots as Redis Cluster, even on one node. A hash tag decides the slot: {user:42}.cart and {user:42}.profile both hash on user:42, so they live on the same cell.

Multi-key commands such as MGET that span cells still work; they pay a fabric hop instead of returning CROSSSLOT. Cross-cell transactions are a separately gated capability (M6).

When the key lives elsewhere

SituationWhat happens
The key is local and in memoryCompletes synchronously. No suspension, no waker.
Another cell owns the keyOne fabric message; the command suspends until the reply arrives.
The record is in the cold tier (M4)An async disk read; other commands keep flowing.
A write in an always namespaceApplied, then acknowledged after the group fsync that covers it.

Each of those waits suspends the command, never the core (law L6). A suspended command resumes through its own state, and checks again what it validated before it waited.

The trade-off, stated honestly

One owner means one hot key is served by one core. A single cell sustains high rates on one key, and RESP3 client-side caching (M7) spreads reads. We document the limit instead of hiding it.

The cell count is fixed for the life of a data directory: each cell recovers only its own shard, and the count is stamped at the first boot. See Configuration for --cells.

Every key, vector, topic partition and log segment is owned by exactly one core. No data-plane locks, no shared mutable state on the hot path.
