Namespaces

A namespace is a logical keyspace with its own durability class, eviction policy and memory budget. Redis SELECT 0..15 maps to default namespaces, which are always memory-only. Named namespaces are created with INF.NS:

127.0.0.1:6379> INF.NS CREATE cache MODE memory EVICTION allkeys-lfu MAXMEMORY 16gb
OK
127.0.0.1:6379> INF.NS CREATE ledger MODE durable FSYNC always
OK
127.0.0.1:6379> INF.NS CREATE sessions MODE durable FSYNC everysec
OK

INF.NS USE ledger binds a connection to a namespace. The choice is per connection, never by key prefix: a command runs in the connection's current namespace, which starts as database 0 (or the server's --conn-default-ns) until INF.NS USE or SELECT changes it. Namespace DDL needs the server started with --data-dir; without one, INF.NS CREATE is refused.

A memory namespace never touches the log. Not rarely: never. Topic namespaces, with retention instead of eviction, arrive with streams and queues in M7.

  • An always acknowledgement is a durability fact. The mutation applies immediately, but the reply is gated: the command suspends until the group fsync covering its log position completes. Throughput comes from grouping, because every concurrent writer shares one fsync.
  • everysec is a real window, stated plainly. Writes are acknowledged on apply and the log is synced on a one-second timer, so a power cut can lose up to the last second of acknowledged writes in that namespace. If that window is unacceptable, use always.

fsync failure is fail-stop

If the device reports an fsync failure, InfinityDB does not retry, degrade or pretend. The durability watermark freezes, no further acknowledgement can be issued against unverified storage, and the process exits with a dedicated code. A repository check makes sure fsync errors can only surface at the allowed fail-stop sites, and a child-process test proves the affected batch is never acknowledged.

Checkpoints, without fork

A checkpoint is a fuzzy snapshot taken by the owning cell in bounded background slices. The live index and records stream to a checkpoint file; records changed mid-checkpoint are covered by the log tail. Then a MANIFEST names the new recovery unit atomically (write new, fsync, rename, fsync the directory), and older log segments are truncated.

  • No fork(), no copy-on-write, no doubled memory during a rewrite.
  • A MANIFEST is published only once the watermark covers the checkpoint's start, so a checkpoint never names state the log has not made durable.
  • A checkpoint I/O failure aborts the checkpoint, never the process: nothing was acknowledged against it, and the log stays authoritative.
  • Operator surface: INF.CKPT [CELL k] [WAIT]. BGSAVE maps onto it with a Redis-identical reply and no RDB file; LASTSAVE reports the newest durable MANIFEST.

Recovery

Recovery is per cell and parallel. Each cell loads its named checkpoint, then replays its log tail from the checkpoint's position. There is no global sequence number and no merge step.

  • While loading, the node answers like Redis: commands outside the exempt set receive -LOADING Redis is loading the dataset in memory. The gate is node-wide, so a cell that has finished still answers -LOADING while a peer replays.
  • A torn final frame, detected by its checksum, is truncated, and replay resumes behind it. That is the defined crash window. Every frame also records the durability watermark at seal time, so recovery can prove when a gap was never fsync-covered and truncate it too. Discarded frames are counted, never silent.
  • Everything else is a refusal, not a guess: a surviving frame that attests coverage past where valid data ends, a MANIFEST that names missing state, an unknown record type. The boot stops and names the evidence. A database that boots with quietly missing acknowledged data is worse than one that refuses and says why.

What a refusal looks like, and what to do about one, is on Observability.
