One log, several products

The hash index, JSON documents, tier files and secondary indexes are projections of the log: rebuilt from it, or loaded from a checkpoint that is itself a log prefix. That leaves one mechanism to make correct instead of one per feature.

Records and frames

A log record is a varint length, a type, flags, a namespace id and a payload. Strings are logged as their new value, never as the operation, so replay is a blind upsert that never depends on what was there before. Other types carry deletes, absolute expiry times, namespace operations, checkpoint markers and document deltas. Unknown types and non-canonical encodings are refused.

An LSN is a (segment, offset) pair inside one cell's log. There is no global LSN and no cross-cell order to agree on, so each cell recovers on its own. The records staged since the last seal go into one frame, written with one write:

header   magic · frame length · record count · first LSN
         · epoch (log life) · seq (frame number in this life)
         · covered LSN (durable watermark when sealed)
body     records
trailer  CRC32C over header and body
padding  zeros up to the next 4 KiB boundary (O_DIRECT segments only)

Recovery uses the epoch, the sequence and the covered LSN to tell a torn tail from lost acknowledged data.

Group commit

A durable write executes, updates the store and stages its record in a ring of whole-frame buffers, 4 MiB each by default (--log-staging-mib), allocated once. At the LOG step the staged records seal into at most one frame per iteration, and its write rides the next iteration's single io_uring_enter. One durability barrier covers every durable write that is due. The durable watermark advances only when a barrier completes, and only over the longest prefix in which every earlier barrier has completed too.

Each namespace chooses when the client hears OK: with FSYNC always the reply waits until the watermark covers its record; with FSYNC everysec it is sent as soon as the write executes and a one-second timer makes sure a barrier runs. Namespaces & durability states the loss window of each. When staging is full, durable writes wait for space instead of failing. A record that could never fit one staging buffer is refused up front with ERR write exceeds durable log staging capacity.

Segments and truncation

The log is a sequence of segment files, shard-N/log/seg-NNNNNN.ilog, 256 MiB each by default. The next segment is created and preallocated in background slices before the current one fills, so rotation is a pointer swap.

The begin LSN of the current checkpoint is the truncation floor. Segments below it are covered by the checkpoint. They are deleted by the control thread, so that freeing a large file stays off the data plane, or, when already zero-filled, renamed into place as the next segment instead.

Checkpoints and the MANIFEST

A checkpoint is fuzzy and taken by the owning cell in bounded MAINTAIN slices under the checkpoint budget. There is no fork() and no stop-the-world pause.

  • The cell stages a checkpoint-begin marker. Its LSN is where replay will start.
  • The cell walks its stores into CRC-protected sections of ckpt-NNNNNN.ick.new, in ordinary log record encodings. A record that changes during the walk is also in the log after the marker.
  • A footer carries per-namespace counts and a digest chained over every section CRC. The file is synced, renamed to .ick and the directory is synced.
  • A new MANIFEST names the checkpoint, its begin LSN, the live segments and any tier files. It is written, fsynced, renamed over the old one and the directory fsynced, so a reader sees the old recovery unit or the new one, never a mix.

A checkpoint starts once the log has grown to about twice the last one, capped so replay stays inside a fixed recovery-time budget. You can also ask for one; BGSAVE maps onto the same checkpoint and writes no RDB file:

127.0.0.1:6379> INF.CKPT WAIT
OK
127.0.0.1:6379> BGSAVE
Background saving started

INF.CKPT [CELL k] [WAIT] needs a node started with --data-dir. An I/O error during a checkpoint abandons that checkpoint, not the process: the previous checkpoint and the log are still valid.

Recovery

Each cell recovers its own log in parallel with the others, in bounded slices. Until every cell has finished, every cell answers -LOADING.

  • Read the MANIFEST. The checkpoint it names must load and the floor segment must exist; anything less stops the boot, never a silent full replay.
  • Load the checkpoint, verifying every section CRC before applying it, then the footer's digest and counts.
  • Replay from the begin LSN, frame by frame. Each frame is validated (magic, length, CRC, recorded position, epoch and sequence continuity) before any of its records applies.
  • Scan past each segment's last valid frame. If a later frame's covered LSN shows that the missing range had been acknowledged as durable, the device lost acknowledged data and the boot stops. Otherwise the gap is an unacknowledged torn tail and the cell continues from it, without rewriting existing bytes.
  • Remove leftovers of interrupted work and reopen the log under a new epoch.

Checkpoint load and tail replay share one idempotent upsert: one recovery path, not two. A graceful stop writes a stop checkpoint, so the next boot replays nothing. An fsync failure on a barrier that protects acknowledged data stops the node, because the page cache can no longer say what reached the disk.
