InfinityDB is a restart. Its predecessor, Vortex, had a SIMD RESP parser, a SwissTable engine, a typed append-only file with crash-point testing, and a concurrency lab that ran more than a thousand experiments. It still missed its throughput, memory and tail-latency targets. It wasn't lack of effort. It was the architecture, and the absence of any gate that could have told us sooner.

1A microbenchmark chose the architecture.

The shared-keyspace lock design scored near-perfect in our concurrency lab, which measured the data plane in isolation. Then the flamegraphs of the real server arrived: most of the CPU went to io_uring completion handling and syscalls, and the effective command batch size was one. The locks we had optimized were never the bottleneck. The I/O plane we treated as plumbing was.

Law derived

The end-to-end system is the unit of validation. InfinityDB's first milestone was an end-to-end skeleton with hard gates, before any feature.

2A shared keyspace made everything global.

Because every reactor mutated one keyspace, every feature threaded through global coordination: a global log sequence number, a merge on replay, epoch validation, stop-the-world rewrites that ended up disabled, and memory accounting that never reconciled.

Law derived · L1

Every byte has exactly one owning core. Persistence, expiry, eviction and accounting become local, single-threaded problems, and each core replays its own log in parallel.

3Fixed-size entries traded memory for elegance.

Cache-line-aligned entries were beautiful in a probe benchmark and ruinous in resident memory. For a cache server, memory is not a tuning parameter. It is the product.

Law derived · L5

Records are variable-size and compact by default, and memory gates are release blockers from the first alpha.

4An invalid experiment rejected shared-nothing.

Our shared-nothing prototype measured cross-core hops far slower than production thread-per-core systems demonstrably achieve. It had benchmarked a bad message fabric, with a wake-up per message, no batching and no pipelining, not the architecture. Nobody checked the result against reality before it bound the decision.

Law derived

Experiments are validated against external reference points before they bind decisions. A result that contradicts production systems is presumed to be an artifact.

5Features came before proof.

We built features on a foundation that had never been proven end to end, then spent months retrofitting fairness budgets, backpressure, admission control and memory attribution.

Law derived

Every milestone ends in STOP gates. Fail one and the train halts; the fix happens in the architecture, not in a later optimization pass.

What we kept

The post-mortem was not a purge. These survived contact with reality and moved into InfinityDB:

  • SWAR integer parsing and perfect-hash command dispatch; the SIMD CRLF scanner came along too, and the RESP parser does not call it.
  • The io_uring backend's typed buffer lifecycle and completion discipline.
  • Crash-point testing, the fault-injection harness and typed durability errors.
  • Clock-sweep eviction with a Count-Min Sketch and the hierarchical timing wheel, now per core.
  • The evidence methodology: replicates, clean trees, memory attribution and the claim ledger.

The order, inverted

InfinityDB inverts the order. One law, one core, one shard, one owner, makes every hard subsystem local. One primitive, the per-core log, makes durability, queues, replication and tiering the same mechanism. One discipline, gates before features and evidence before claims, makes sure we never again publish a target we haven't earned.
