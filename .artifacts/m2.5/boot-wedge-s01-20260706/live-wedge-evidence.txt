=== interpretation of the v2 cycle-42 capture (2026-07-06) ===
The narration named the wedge (cell 3, setup:driver) — ADR-0026 D2 held.
Reading the samples against a healthy-process control changes the D3 mechanism:

1. cell-3's thread is ABSENT from /proc/<pid>/task across all 6 samples
   (healthy control run shows comm=cell-3 present from spawn, since
   std::thread::Builder::name sets the comm before user code runs).
   A thread blocked inside io_uring_setup would still be listed (D or S
   state with a wchan). Absence means the thread had EXITED.
2. The three live cells sat in normal idle (S, io_cqring_wait).
3. System counters at capture: IO PSI full avg10=93.96 (saturated),
   Dirty ~2.0 GiB, Writeback 0; allocstall_*=0, compact_stall=0,
   compact_fail=0, memory PSI=0.00, MemFree ~20 GiB.

Mechanism (revised): io_uring_setup did not stall — it FAILED fast
(no allocation stalls anywhere), cell_main returned Err through
`make_driver()?` between mark(12) and mark(13), and main's in-order join
loop (blocked joining cell 0, which never exits) swallowed the error
forever. The board kept publishing the dead cell's last phase; the
narrator honestly reported a corpse as "not ready". Silent-wedge shape =
server-side error-swallowing defect + kernel-side fast setup failure
under writeback pressure.

Fixes applied (same day):
- bins/infinityd/src/main.rs: cell threads fail-stop at the thread
  boundary — setup/loop Err or panic prints `cell N failed: <errno>` and
  exits the node (L9 §8.4 fail-stop, no silent corpses).
- crates/inf-runtime/src/uring.rs: the setup-flag fallback chain retries
  only on EINVAL; ENOMEM-class errors propagate instead of silently
  stripping single_issuer/defer_taskrun from one cell.

Healthy-process thread-listing control (for the absence claim):
  tid comms observed: infinityd, inf-control, cell-0..cell-3,
  iou-wrk-<cell tid> x6 per cell.
